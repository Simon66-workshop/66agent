# 编程助理 · 提交程序审计 SOP

**适用 Agent**：编程 Agent  
**对接**：Grok办公助理（`skills/办公助理_程序审计SOP.md`）  
**最后更新**：2026-08-22  
**目标**：编程任务「声称完成」时，必须打成标准 **审计提交包**，交给办公助理做 Bug + 功能完善度门禁。

---

## 1. 何时必须提交审计

- 辉哥说「做完了 / 交付 / 提审 / 验收」  
- 你认为主路径已实现、准备收尾  
- 多文件或核心逻辑变更后  
- 修复了上一轮审计的退回项后（**复审**）

小改动（纯文案、一行配置）可问辉哥是否免审；默认：**能提审就提审**。

---

## 2. 提交前自检（你自己先做）

1. 对照开任务时的 **验收标准** 逐条勾选  
2. 按「如何验证」真实跑过（或明确写无法在本环境验证）  
3. 列出已知限制，不藏  
4. 不把 TODO / 半成品标成完成

自检不通过 → 先修再提交，不把烂包丢给办公助理。

---

## 3. 标准【程序审计提交包】格式（强制）

```text
【程序审计提交包】
提交方：编程 Agent
时间：（Asia/Shanghai）
类型：初审 / 复审（若复审，附上一轮报告要点）

1. 项目/模块：
2. 目标：
3. 范围：
   - 做了：
   - 明确没做：
4. 验收标准：
   - [ ] 标准1
   - [ ] 标准2
5. 变更文件列表：
   - path/to/file — 变更摘要
6. 如何验证：
   - 步骤/命令
   - 预期结果
7. 编程侧自检：
   - 已勾选验收：是/否
   - 已知问题：
8. 请重点审：
9. 建议可调用的审计模型：Grok4.6 / Cursor+Opus4.5 / Cursor+GPT5.6sol
```

---

## 4. 交给办公助理的方式

你无法直接私信办公助理时，按总控约定：

1. 在回复辉哥时 **完整输出提交包**  
2. 明确写：`请交办公助理按 skills/办公助理_程序审计SOP.md 审计`  
3. 若辉哥在 Group：同样贴出提交包，@ 或注明办公助理  
4. 办公助理退回后：只修清单内项，再发 **复审包**（类型=复审）

---

## 5. 多模型在「提交侧」怎么用

提交前可用（可选，提高一次通过率）：

| 工具 | 用途 |
|------|------|
| **Cursor + Opus 4.5** | 提交前深自检复杂逻辑 |
| **Cursor + GPT 5.6 sol** | 补测例、找遗漏边界 |
| **本地 Grok 4.6** | 对照验收标准做提交前清单 |
| **Codex** | 仅用于修审计指出的问题，不用于「审自己」当唯一依据 |

原则：谁写的代码，不独享最终审计权；**门禁在办公助理**。

---

## 6. 审计结果怎么处理

| 结论 | 你的动作 |
|------|----------|
| 通过 | 收尾；重要坑写入 skills/工作记忆；推 GitHub（如适用） |
| 有条件通过 | 先清必须补的小项，再简短确认 |
| 退回 | 严格按 P0/P1 清单修；不扩 scope；修完复审包 |

---

## 7. 与多模型编程分工的关系

仍遵守 `skills/多模型编程分工SOP.md`：  
- Codex / Cursor：执行修复  
- Opus：难点  
- 编程 Agent：拆任务、收包、对验收  
- 办公助理：完成态质量门禁  

---

*编程任务闭环 = 实现 → 提交包 → 办公审计 →（退回则修复）→ 通过后学习闭环。*
