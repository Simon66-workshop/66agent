## A. Bug 清单

严重度定义：**高** = 按 v0.1 直接跑，会产出错误排序/错误动作或根本跑不起来；**中** = 会系统性偏差或让 7 天数据不可用于校准；**低** = 文字/一致性问题，不改也能跑。

### A.1 热度打分层（第四层）

**B-01 百分位归一化在小样本下失真，且跨日不可比、每天必有「热」**
- 所在层：四
- 问题：四项指标「换算成当日候选池百分位」（**FACT** D#L42），而日池上限 25 条（**FACT** D#L17；S:radar-scout.md#L7「25 条是最大候选池」）。n≤25 时百分位步长 ≥4 分；且百分位是相对量，「热度≥80」在任何一天都恒有约 20% 的条目命中，与当天是否真的有热帖无关。这使 D#L52「热度≥80 的 P0/P1 当天处理」变成「每天固定加急前 20%」，也使不同日期的热度分完全不可比，Self Optimizer 无法据此校准权重。
- 复现/反例：OBS 真实样本 n=21，按浏览量算百分位步长 4.76；@Fred834567 的「戒断故事」帖 325,137 浏览排 95.2 分位（OBS 中人工已标「降权，不进 66 选题」），@xiangxiang103 的 Qwen-Image 实操帖 158,061 浏览排 90.5 分位——两者在 v0.1 下同属「热度≥80 加急」，但前者是噪声。极端例：某日池 5 条浏览 200/300/400/500/600，600 那条得 100 分位。**INFERENCE**（算法性质推导，数字来自 OBS）。
- 严重度：高
- 修复：改为**绝对刻度 + 上限截断**：超常倍数用 `min(log2(ratio)/log2(8), 1)`（≥8× 满分、1× 为 0，3× 约 0.53 与 D#L44「≥3 倍标爆款」相容）；速度用 `log10(views/小时)` 类刻度；评论/收藏率用固定区间。百分位只作展示字段，并同时输出 `n`。攒够 14 天后再用滚动基线替代固定刻度。刻度参数在 7 天影子运行后用数据定，不在 v0.2 里拍脑袋。

**B-02 「作者历史浏览中位数」冷启动、自包含、年龄混杂，且对 Radar 候选根本算不出来**
- 所在层：四（依赖一）
- 问题：超常倍数 = 本帖浏览 ÷ 作者历史中位数（**FACT** D#L44），历史来自「每号近 10 条原创帖」（**FACT** D#L14）。三个漏洞：(a) 中位数把本帖自己算进去；作者只有 1 条时比值恒为 1.0；(b) 10 条帖年龄混杂，3 小时前的帖与 3 天前的帖浏览量不可比，年轻帖被系统性低估；(c) 5 个 Radar 的候选作者不在七号池内，没有历史，也没有预算去拉——每新作者需 `User $0.01 + 10×Post $0.005 = $0.06`，25 个作者 = $1.50，超 D#L14 的 $0.50 硬上限三倍（**INFERENCE**，价格 FACT 见 §0）。
- 复现/反例：OBS 样本按作者分组：@jiroucaigou 仅 1 帖（中位数=自身，比值 1.0）；@AI_DVD6 2 帖；@Fred834567 4 帖中位数 16,777、最高 325,137，比值 19.4（噪声帖反而「最爆款」）；@AI_DVD6 一条 3 小时前的帖 164 浏览与同号 23 小时前的帖 37,225 浏览同池比较。**FACT**（OBS 数据）。
- 严重度：高
- 修复：(1) 基线只用「发布 >48h 且不含本帖」的历史帖；(2) 基线样本 <8 条时该项记 `UNKNOWN`，权重按 B-07 重归一；(3) Radar 路径的候选**不算**超常倍数，只算速度与收藏率；(4) 基线放 state.json 并按 B-24 进仓库。

**B-03 增速需隔天二次采样，但 routine 每天只跑一次，且与「发布 >48h 降权」正面冲突**
- 所在层：四（依赖背景 routine）
- 问题：增速 = 「同帖隔天二次采样的每小时增长；发布 >48h 降权」（**FACT** D#L45）；routine 上海时间每天 08:57 一次（**FACT** D#L14）。推演：某帖 D 日 09:00 后发布 → D+1 08:57 首采（帖龄约 24h，无增速）→ D+2 08:57 二采（帖龄约 48h，刚有增速就落进降权区）。结果：增速项在能算出来的那一刻恰好被降权；观察期第一天（09-25）所有条目增速为空。25% 权重形同虚设。**INFERENCE**（由 D#L14、D#L45 推）。
- 复现/反例：任取一条 09-25 10:00 发布的帖按上述时间轴走一遍即可。
- 严重度：高
- 修复（两选一，推荐前者）：(a) 改为**单次采样速度** `views ÷ 已发布小时数`（`created_at` 由 API 给，绝对时刻），无需二采，帖龄 <2h 记 UNKNOWN；(b) 若坚持二采，同日加一次 20:57 采样——X 文档「同一资源 24h 内重复请求只计费一次」（**FACT** §0），12h 后再拉同一批帖预计不再计费，但是否覆盖时间线端点须在 console 上实测（**UNKNOWN**：需一次真实两采的 console 计费读数）。

**B-04 评论率作为热度信号在真实样本中反向选择噪声帖；低浏览量放大噪声；除零未定义**
- 所在层：四
- 问题：评论率 = 评论 ÷ 浏览（**FACT** D#L47）。低浏览帖的比率天然高；引战/会务/互动引导帖评论率高；真正有「可复用方法」的帖往往收藏多、评论少。
- 复现/反例：OBS 21 帖按评论率排序，前 5 依次是 @jiroucaigou OKX 会务（1.80%）、@Fred834567 Pexo 产品帖（1.31%）、@NFTCPS KOL 清单（1.05%）、@NFTCPS 热门标签站（0.71%）、@NFTCPS 土狗监控（0.62%）——全部是 OBS 人工标「降权，不跟」的簇；而两条收藏最高的实操帖 @xiangxiang103 Qwen 锁（3,115 收藏，评论率 0.024%）、@AI_DVD6 筛潜客（378 收藏，0.054%）排在倒数。@AI_DVD6 有一条 164 浏览 0 评论；若某帖浏览为 0 则除零。**FACT**（OBS 数据）。
- 严重度：高
- 修复：(1) 用**收藏率** `bookmark_count ÷ impression_count` 替代或与评论率对半（`bookmark_count` 在 `public_metrics` 内免费同返，**FACT** §0）；(2) 浏览 < 某门槛（门槛用 7 天数据定，暂建议 1,000）时比率项记 UNKNOWN；(3) 分母加平滑 `(x+α)/(views+β)`，α、β 待数据定。OBS 分析者自己也是按收藏而非评论选的（OBS「价格帖回复多、收藏少。配方帖收藏高。66 的写法取配方这头」）。

**B-05 跨号共振：稀疏二值量做百分位退化；两两比对成本 O(n²)；对标号互相转述不是独立信号**
- 所在层：四
- 问题：跨号共振 = 72h 内 ≥2 个对标号讲同一话题，同题由 Jev 判（**FACT** D#L46）。(a) 7 个号下，该量大多数条目为 0，少数为 1，百分位下「0」的分位取值依并列处理方式在 0～45 之间摆动，20% 权重被实现细节决定；(b) 判同题若两两问 Jev，70 帖 = 2,415 对，25 帖 = 300 对，每天一次，成本与延迟未估；(c) 七号之间存在引用/转帖链时，「共振」只是回声。
- 复现/反例：OBS 中「GPT-6 Sol 降价」在 @gengdaJ 与 @Saccc_c 两号出现（**FACT** OBS §4），是 21 帖里唯一跨号簇；其余 19 帖共振为 0——百分位在此退化。
- 严重度：中
- 修复：(1) 共振改为**离散计数**（0 / 1 / ≥2 个独立账号）直接映射 0 / 50 / 100，不做百分位；(2) 聚类用「增量法」：按发布时间排序，每帖只与当日已有簇的种子帖问一次 Jev（n×k 而非 n²），或由宿主模型一次性对 ≤70 条标题聚簇；(3) `referenced_tweets` 含引用/转帖指向同簇者不计独立账号（**FACT** 字段存在，§0）。

**B-06 抖音替代指标与 X 指标混池比较**
- 所在层：四
- 问题：「抖音多不公开播放量：用赞/评/藏/转显示数作替代并注明」（**FACT** D#L48）。若与 X 候选放进同一「当日候选池」做百分位，赞数与浏览数在同一列排名；评论率、超常倍数在抖音侧无分母，无法计算。「注明」不解决可比性。
- 复现/反例：抖音某作品 5,000 赞与 X 某帖 5,000 浏览进同一列即可。**INFERENCE**。
- 严重度：中（若抖音侧 7 天内确实不跑则为低，见 B-25）
- 修复：**分平台池**，各自公式：X 用 B-01～B-05 修订版；抖音用 `赞/评/藏` 三项的绝对刻度，不算超常倍数与速度（无播放量、无二采）。Ledger 加 `platform` 字段，禁止跨平台比较热度分。

**B-07 缺失值处理未定义：「拿不到留空不填 0」与加权求和冲突**
- 所在层：一 → 四
- 问题：采集层规定「拿不到留空不填 0」（**FACT** D#L19；S:douyin-daily-opportunity-radar.md#L41「未知不填 0」），但热度加权和（D#L43）没有说空值怎么办。若实现时空值当 0，该条被系统性压低；若当中位数，则被人为抬高。
- 复现/反例：OBS 中 @jiroucaigou、@AI_DVD6 各有一帖「收藏 未找到」（**FACT** OBS §6、§另外两簇）。
- 严重度：中
- 修复：对可得项按权重重归一（`H = Σ w_i·s_i / Σ w_i`，i 仅取非空项）；非空项 <2 时 `H = UNKNOWN`；输出 `coverage` 字段记录哪几项可得。

**B-08 「≥80」在两条刻度上重名：热度百分位 ≥80 与价值分 P1≥80**
- 所在层：五、六
- 问题：D#L52「热度 ≥80 的 P0/P1 当天处理」是热度分；D#L60–61「P1 ≥80 或任意 P0 当天必须出草稿」「P0 或 P1 ≥80 且满足深拆条件」是价值分（对应 S:self-optimizer-2.md#L25「if any P1≥80 … ship 1 draft」）。同一文档两个「≥80」，实现或口头传达时极易混用，把「热」误当「高价值」直接送进出稿链——这正是 D#L52 自己要防的「热度分不能拉入 P0」。**FACT**（原文两处）+ **INFERENCE**（风险）。
- 严重度：中
- 修复：命名分离：价值分 `V`（0–100，档位依据），热度 `H`（0–100，仅排序）；加急标记改为布尔 `HOT`，规则写成「`HOT = (H≥阈值)`，`HOT` 只改同档内顺序与处理时限」。

### A.2 Jev 语义筛选层（第三层）

**B-09 九题极性不一、「P(是)≥0.8 直接采用」语义含混；硬门禁与软判断混在一套阈值里**
- 所在层：三
- 问题：Q1/2/5/7/8 为正向题（是=好），Q3「只是新闻复述」、Q4「引流/带货/招聘帖」、Q9「原帖已把答案讲完」为负向题（是=坏），Q6 是两两比对题（**FACT** D#L30–38）。阈值只写「P(是) ≥0.8 直接采用；0.5–0.8 交宿主模型复核；<0.5 按否」（**FACT** D#L39），对负向题「采用」意味着丢弃，对 Q4 这种一票否决题，<0.5「按否」等于放行疑似引流帖。仓库版 typesafe-ai 明说「weighted scores suit compensating preferences; an "any serious violation" rule needs separate conditions」（**FACT** R:skills/typesafe-ai/SKILL.md#L139-L140）。
- 复现/反例：某帖 Q4 得 0.45 → 按 D#L39「按否」= 不是引流 → 放行；某帖 Q3 得 0.85 → 「直接采用」= 采用什么？
- 严重度：中
- 修复：给每题写**动作表**（见 E 节 v0.2 §三）：Q4、Q3 为硬门禁，`p≥0.5` 即挡（宁可误杀，人工可从 Ledger 捞回）；Q1/Q2/Q8 为软得分进复核；Q6 改为聚簇实现（B-05）；Q5/Q7/Q9 只作标注，不作门。

**B-10 灰区 0.5–0.8 的成本与漂移无估算、无记录，无法校准**
- 所在层：三
- 问题：每天最多 25（Radar）+ 70（七号）+ 20（抖音发现）≈ 115 条候选 × 9 题 ≈ 1,000 次 Noul（**INFERENCE**，上限来自 D#L17–18、D#L14）；灰区占比未知，灰区条目要过宿主模型复核，宿主模型成本随灰区占比线性放大；设计未要求记录每题概率，10-01 校准时没有原始分布可看。仓库版 typesafe-ai 提示「A Noul near 0.5 means similar probability for yes and no, not medium intensity」「validate their performance in the target domain」「Treat cookbook thresholds … as examples to evaluate, not universal rules」（**FACT** R:skills/typesafe-ai/SKILL.md#L134-L135、#L143、#L148-L149）。
- 严重度：中
- 修复：(1) 每次调用写 JSONL：`{post_id, question_id, p, model_version, decision, human_outcome}` 进仓库；(2) 题数从 9 减到 5（Q1 相关、Q2 可复用、Q4 引流门禁、Q8 决策问题、Q3 新闻复述门禁），Q5/7/9 由宿主模型在价值打分时顺带判；(3) 7 天后按分布再定灰区边界；(4) 灰区复核每日设上限（建议 ≤10 条），超出按「否」并记 `GREY_CAPPED`。
- UNKNOWN：需要 7 天真实的 `p` 分布与 Jev 版本号（工作记忆里出现过 `jev-1.13.0`，R:Grok办公助理_工作记忆日志.md#L83）才能判断灰区占比与漂移。

**B-11 Jev 不可用在现实中是常态，但设计没有降级路径**
- 所在层：三（影响六）
- 问题：设计只说「无法调用标 JEV_NOT_RUN」（**FACT** D#L39），未说标了之后流水线怎么走。仓库工作记忆多次记录 Jev 未跑：「本机 `TYPESAFE_API_KEY` 未设，本轮…未调 Jev」（**FACT** R:Grok办公助理_工作记忆日志.md#L91、#L94、#L96）、「Auto-review 拦截外呼 api.typesafe.ai」（**FACT** 同文件 #L82）、「Jev 未调（TYPESAFE_API_KEY 未设）」（#L90）。若 JEV_NOT_RUN 时宿主模型接管全部 9 题，成本与漂移都变了，而产出只写一句 JEV_NOT_RUN，事后无法区分两套判断。
- 严重度：高（可执行性）
- 修复：明确「JEV_NOT_RUN → 宿主模型按同一题表、同一 JSON 结构作答，`source=HOST`，并在当日报告顶部醒目标注；连续 2 天 JEV_NOT_RUN 触发人工检查 key/出站」。7 天试运行前必须先跑通一次真实 Jev 调用并把返回体（去密钥）留档。

### C.3 整体结论

**现在能不能按 v0.1 跑 7 天试运行？**

- 按 v0.1 原文**不能**当作「会影响出稿与深拆的正式流程」跑：第四层对大部分候选算不出来、算出来的方向在真实样本上反了（B-01～B-04、B-13），第三层在 Jev 不可用时没有路径（B-11），第六层容量会把未核数字推进草稿（B-17）。**INFERENCE**（基于上述 FACT）。
- **能**以「X 侧、影子模式」跑 7 天：照 D#L14 的 08:57 routine 采七号数据 + 用 O-2 补 Radar 候选指标，按 v0.2 公式算 H 但只记录不路由，档位与出稿完全沿用现行 Evidence Judge / Content Converter / self-optimizer-2 规则。这 7 天的目的不是校准权重，而是拿到第一批 (H, V, 人工 top-5, Jev p, 成本) 数据。

**前提条件（缺一项则 7 天数据不可用）：**

1. 真实 Jev 调用跑通一次并留档（去密钥），或明确 7 天全程 `source=HOST` 并写进每日报告顶部（B-11）。
2. `state.json` + 每日原始 `public_metrics` 快照进仓库分支（B-24）。
3. Ledger 加列 `Platform, H, H_coverage, V, JevRun, JevP, CostUSD` 并由程序写行（B-21）。
4. 辉哥每天 2 分钟点选人工 top-5 作为标签（O-1）。
5. 每次 run 记成本估算与 console 读数，硬上限保持 $0.50（O-12）。
6. 试运行范围写明「X 侧」；抖音待 routine 回读（B-25）。
7. 深拆 ≤3/周，「当天必出」改为「草稿或深拆工单」（B-17）。
8. 试运行期热度权重、Jev 阈值、题表归黄区（B-22）。

**10-01 周总结能得出什么、不能得出什么：** 能得出 H 各分项分布、H top-5 与人工 top-5 重合数、Jev 灰区占比、真实日成本；**不能**得出「权重该调成多少」（无终局标签）与「Jev 阈值该定多少」（7 天不足以看漂移）。
